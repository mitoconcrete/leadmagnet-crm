# ADR 0016. 대시보드 주기 갱신과 마지막 갱신 시각 표시

- 상태: 채택 (2026-09-10)

## 맥락
대시보드와 캠페인 상세의 성과 숫자는 마운트 시 한 번만 조회된다. 운영자가 화면을 켜 둔 채 SNS 반응을 보려면 새로고침을 반복해야 하고, 지금 보이는 숫자가 언제 기준인지 알 수 없다. 기획에 없던 항목이라 가정을 세워 기록한다.

## 결정
- 성과 데이터(대시보드 캠페인 표·채널 표, 캠페인 상세 stats·채널 breakdown·신청 명단)는 **30초 간격**으로 자동 재조회한다. 간격은 `lib/polling.ts`의 상수 하나로 둔다.
- 화면에 **"마지막 갱신 HH:MM:SS"** 와 **"지금 갱신"** 버튼을 표시한다. 시각은 마지막으로 성공한 응답 시각(브라우저 시계, KST 표시)이다.
- 탭이 보이지 않으면(`document.hidden`) 폴링을 멈추고, 다시 보이면 즉시 1회 갱신한다.
- 갱신 실패 시 이전 데이터를 유지하고 "갱신 실패(마지막 성공 HH:MM:SS)"를 표시한다. 토스트는 첫 실패에만 띄운다.
- 구현은 작은 훅 `usePolling(fetcher, intervalMs)` 하나로 통일한다. 외부 데이터 라이브러리는 추가하지 않는다.

## 근거
- 30초는 "SNS에 올린 뒤 반응을 지켜보는" 용도에 충분히 짧고, 관리자 1~2명이 켜 둔 화면이 만드는 부하(요청 2~3개/30초)는 무시할 수 있다.
- 서버 푸시(SSE/WebSocket)는 이 규모에서 과하다. 연결 관리·재접속·프록시 설정이 늘고 얻는 것은 몇 초의 지연뿐이다.
- "언제 기준인가"를 보여 주지 않는 자동 갱신은 오히려 혼란을 준다. 시각 표시가 기능의 절반이다.

## 대안
- react-query/SWR: 폴링·캐시가 내장돼 있지만 의존성과 학습 비용이 늘고, 이 화면의 요구는 훅 20줄로 충분하다.
- 서버 푸시: 위 근거로 보류. 트래픽이 커져 실시간이 중요해지면 첫 후보.

## 결과
- `usePolling` 단위 테스트(가짜 타이머로 간격·visibility·실패 유지)와 화면 테스트(시각 표시·버튼)를 추가한다.
