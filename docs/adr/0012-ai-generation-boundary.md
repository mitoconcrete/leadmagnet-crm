# ADR 0012. AI 생성은 시스템 경계 밖, 입력 계약과 샘플로 증명

- 상태: 채택 (2026-09-09)

## 맥락
과제는 "AI가 만든 단일 HTML 폼"을 전제로 하되 실제 AI 연동은 범위 밖으로 둔다. 그래도 "AI 산출물이 이 시스템에서 그대로 동작한다"는 것은 보여야 한다. 흉내용 생성 엔드포인트를 만들면 범위 밖 기능을 반쯤 구현하는 셈이 되고, 아무것도 안 하면 AI 전제가 문서에만 남는다.

## 결정
- 시스템 경계는 "HTML 파일 등록"이다. 생성은 밖에서 한다. 코드에 AI 호출·스텁·키를 두지 않는다.
- 대신 세 가지로 증명한다.
  1. **입력 계약** `docs/ai-generation-guide.md`: 받는 HTML의 조건표와 운영자가 AI에 붙여넣는 프롬프트 템플릿.
  2. **실제 AI 생성 샘플** `samples/*.html`: 그 프롬프트로 생성한 폼. 파일 머리에 도구·프롬프트 값을 주석으로 남긴다. e2e 픽스처와 별도로, 평가자가 바로 등록해 시연할 수 있는 용도.
  3. **관리자 화면 안내**: 템플릿 페이지에 프롬프트 복사 박스. 제품 흐름에서 AI 단계의 위치를 보여 준다.
- 확장 지점: 향후 생성 모듈은 `TemplatesService.create`를 같은 입구로 쓴다. 키는 `.env` `AI_API_KEY` → `loadEnv()`. 격리(ADR 0003)·제출 계약(ADR 0002)·집계(ADR 0006)는 영향 없음.

## 근거
- 이 시스템의 가치는 "어떤 AI가 만들었든 `<form>`만 있으면 격리해 띄우고 제출을 CRM에 넣는다"는 데 있다. 계약을 명확히 하는 것이 특정 AI 호출 코드보다 재사용성이 높다.
- 샘플은 실제 AI 산출물이라 "동작 가능"의 증거이면서 시연 자료다. 검증 규칙(`<form>` 필수 등)이 왜 그렇게 정해졌는지도 샘플로 설명된다.

## 대안
- mock 생성 엔드포인트(`POST /api/admin/templates/generate`): 흐름은 보여 주지만 범위 밖 기능의 반쪽 구현이고, 실제 연동 시 어차피 다시 설계한다.
- 프롬프트 입력 → 실제 LLM 호출: 키·비용·비결정성이 테스트와 평가 환경에 들어온다. 범위 밖.
